A script in the engine is a short program written as nested brackets, such as (if (near-player) (print "Hello")). Before it can run, it is compiled into a flat array of 32-bit numbers called cells, which a small virtual machine steps through one at a time.

This article describes a cell layout with one particular property: any piece of a compiled script can be lifted out and copied somewhere else without being changed. An entity can keep only the cells for its own behaviour, and everything else the script produced can be thrown away. Getting that property costs very little, but it has to be designed in from the start, because it rules out the obvious way of pointing from one cell to another.

Part I describes the format. Part II builds the compiler that produces it, first piece by piece and then as a single function with no recursion. Part III covers what the virtual machine has to do to run it.

How to read the code in this article

The listings are pseudocode. They are close to C, and read top to bottom, but they leave out error handling and memory management so that the shape of the algorithm stays visible. push, pop and top act on small fixed-size stacks. A line that says error means: log the problem, give back the memory, and return nothing. var x = 0 declares a new variable, and a plain x = 0 assigns to one that already exists.

Part I · The format

1What we are building

Take two lines of script:

Listing 1. Two root expressions
(print "Hello World")
(print "Goodbye")

Each line that stands on its own is a root expression. The compiled output keeps them separate and in order: the code for one root, then the strings it uses, then the code for the next root, then its strings.

Listing 2. The shape of the output
[code][strings]  [code][strings]
 root 1           root 2

Some commands take another expression as an argument, without running it straight away. if is the obvious one: (if (print "Hi") (print "Bye")) must decide which of its two branches runs. An argument like that is a sub-expression, and the compiler treats it exactly like a root: it gets its own code and its own strings, and it is placed after the expression that owns it.

Listing 3. Sub-expressions get the same treatment
[if: code][if: strings]
  [Hi: code][Hi: strings]
  [Bye: code][Bye: strings]

Every block of the form [code][strings], whether it came from a root or a sub-expression, is called a unit. The rest of the article is about how units are laid out, how they refer to each other, and how to produce them.

2Cells

One 32-bit number, two possible meanings, told apart by the top bit.

A cell is a u32. The top bit says what kind of cell it is, and the other 31 bits hold its contents.

TypeTop bitRemaining bitsUsed for
Data031 bits of value Numbers, string offsets, sub-unit offsets, lengths, string characters
Call115 bits of command id, 16 bits of argument count Running a command

Code is written in postfix order: the arguments come first and the call comes last. (print "Hi") becomes a data cell that says where "Hi" is, followed by a call cell that says print, with one argument. When the VM reaches the call it already has the argument in hand, so nothing needs to look ahead.

A string is stored as one data cell holding its length, followed by its characters packed four to a cell. "Hi" takes two cells; "Hello World" takes four.

3Units

Everything a unit needs lives inside it, and it only ever points forwards into itself.

Every unit has the same layout:

Listing 4. One unit
[unitLength]      total cells in this unit, sub-units included
[poolOffset]      cells from the start of the unit to its string pool
[code]            postfix: arguments, then the call
[return]          a call cell meaning "leave this unit"
[string pool]     length-prefixed strings
[sub-unit] ...    each one is a complete unit

The first cell of a unit is its base. Three rules make the whole scheme work:

  1. Every reference is relative to the unit. A sub-expression argument is stored as “the unit that starts 6 cells into this one”, never as “the unit at cell 6”. A string argument is stored as “the string 0 cells into this unit’s pool”, and the pool’s own position, poolOffset, is counted from the base too.
  2. Sub-units live inside their parent. They are placed after the parent’s string pool, and the parent’s unitLength counts them. A unit and everything it can reach form one contiguous run of cells.
  3. The header holds lengths, not jumps. The code always starts straight after the header, at base + 2, so the VM never needs to jump to reach it. poolOffset says where the strings are, and unitLength tells anything that wants to copy a unit how many cells to take.

The pool comes after the code rather than before it for the compiler’s sake. Code at a fixed position can be written as soon as it is read, without first finding out how big the pool will be, so each unit is compiled in a single pass. Section 7 shows how.

A whole script is just its root units placed one after another, with a single 0 cell at the end. A unitLength of zero can never happen in a real unit, since the header alone is two cells, so it serves as the end marker.

Listing 5. A whole script
[root unit][root unit] ... [root unit][0]

4A worked example

Here is (if (print "Hi") (print "Bye")) compiled, cell by cell. The root unit holds if and has no strings of its own. Its two arguments are sub-units, so its code is two offsets and a call.

Walk through the Hi unit, which starts at cell 6. Its first cell says it is 7 cells long, and its second says its pool starts 5 cells in, at cell 11. Its code starts straight after the header, at cell 8, with $0: the string 0 cells into the pool. That is cell 11, which holds the length 2, followed by the characters Hi in cell 12. Then pr/1 prints it, and ret hands control back to whoever ran the unit.

The root unit’s length is 20 because it includes both sub-units. It has no strings, so its pool is empty: poolOffset is 6, just past its ret, where a pool would start, and nothing ever reads from there.

5Copying a unit

Suppose an entity only needs the Hi branch. Copying it is one call:

Listing 6. Extracting a unitno fix-ups
var length = cells[base]
memcpy(newCells, cells + base, length * sizeof(u32))

In the new buffer the unit starts at cell 0 instead of cell 6, and nothing inside it needs to change. Its poolOffset still says “my pool is 5 cells from my base”, its $0 still means “the first string in my pool”, and the base has moved along with both. If the unit had sub-units of its own, they would have been copied too, because they sit inside its length.

The same works for a whole root: copy unitLength cells and you have a self-contained program. Once every entity has copied the unit it needs, the original compiled script can be discarded.

Why not absolute indices?

With absolute indices, cell 8 would say “the string at cell 11”. Copy the unit to cell 0 and that is now wrong, so every reference would need to be found and rewritten. To find them you would need to know which data cells are references and which are plain numbers, which means decoding the code. Relative offsets avoid the question entirely.

Summary
  • A unit is a header, code, a return, a string pool, and its sub-units, in that order.
  • Every reference is an offset from the unit’s first cell, or from its pool, whose position is itself an offset from the first cell.
  • A unit contains everything it can reach, so unitLength cells starting at its base can be copied anywhere.

Part II · The compiler

6Params and the expression stack

The compiler needs to know, for every argument, what kind of argument the command expects in that position.

Each registered command has a params string. Its first character is what the command returns, and each character after that describes one argument.

CharacterMeaning
vVoid: returns nothing (return position only)
nA number
sA string
xA sub-expression, compiled as its own unit
+The previous argument kind, repeated any number of times

So if might be vxx and print might be vs. While reading tokens, the compiler keeps a stack of open expressions. Each entry records the command and how many arguments have been read so far:

Listing 7. An open expression
Expression:
  commandId
  command
  argIndex          how many arguments have been read so far

currentParam(e):
  the kind of argument e expects next
  return e.command.params[1 + e.argIndex], with '+' repeating the character before it

The one rule that drives everything else: when a ( appears and the expression on top of the stack expects an x, the new expression is not part of the current unit. It will become a unit of its own later, so for now the compiler skips over it to its matching ).

A ( in any other position, such as a command that returns a number being used as a number argument, is an ordinary nested call. It is compiled inline, in postfix order, as part of the current unit, and its strings go in the current unit’s pool.

7Strings as you go

Because the pool comes after the code, a string’s place in the pool can be decided the moment the string is first seen.

If the pool came first, the compiler would have to read each unit twice: once to collect its strings and learn how big the pool is, and again to write the code after it. With the pool after the code, the code always starts at base + 2, and a string argument is stored as an offset into the pool rather than from the base. That offset depends only on the strings that came before it in the same unit, so it is known as soon as the string is read.

While it compiles a unit, the compiler keeps a short list of the strings the unit has used so far. Each entry is a slice of the script source, so nothing is copied, and the place in the pool that the string has been given:

Listing 8. Giving a string its place in the pool
UnitString:
  string            a slice of the script source
  poolOffset        where the string will start in the pool

on a string argument
var entry = find token in strings
if entry is none:
  if strings is full: error "Too many strings"
  entry = push strings { string: token, poolOffset: poolCells }
  poolCells += stringCellCount(token.length)
cells[cellIndex++] = data(entry.poolOffset)

after the unit's return
cells[base + 1] = cellIndex - base   poolOffset
for each entry in strings:
  cellIndex += writeString(cells[cellIndex], entry.string)

poolCells counts how many cells the pool will need so far, and stringCellCount is one length cell plus one cell for every four characters, so each new string is given the next free place. When the pool is written at the end, the strings go out in the order they were added, which puts each one exactly where its poolOffset says.

A string used twice in one unit is found in the list the second time and stored once. Looking it up is a plain string comparison over a short list. The compiler never reads back from the cell buffer, so it does not matter what was left in that memory before. Strings are not shared between units: a copied unit has to carry its own, so sharing would break section 5.

8Compiling one unit

A unit is compiled by reading its tokens once, from its opening ( to the matching ). The tokeniser’s position in the source text, cursor, is all it needs to start, so a unit is identified by the cursor of its opening (. As it reads, the loop:

  • Checks each argument against the param it fills, and each command against privileged if the command is protected.
  • Writes numbers straight into the code, and strings as pool offsets, as in listing 8.
  • Writes the call cell at every ). Because the arguments were written first, the output is postfix without any extra work.
  • When it meets a sub-expression in an x position, writes a placeholder cell and pushes a frame for a new unit that has not been compiled yet. The frame records where the placeholder is and where the sub-expression starts in the source. Frames are explained in the next section.
Listing 9. Compiling one unita single pass
cellIndex = base + 2                 after the two header cells
clear exprs
clear strings
var poolCells = 0
var cursor = unit.exprStart
var firstChild = units.length

do:
  var open  = cursor
  var token = nextToken(script, &cursor)

  '('    : var name = nextToken(script, &cursor)
           var command = lookup(name) or error "Unknown command"
           if command.protected and not privileged: error "Command is protected"
           if exprs not empty and currentParam(exprs.top) == 'x':
             if units is full: error "Too many sub-expressions"
             push units { exprStart: open, parentBase: base,
                          placeholder: cellIndex, compiled: false }
             cells[cellIndex++] = placeholder
             skipToMatchingClose(script, &cursor)
             exprs.top.argIndex++
             continue
           if exprs not empty:
             check returnType(command) fits currentParam(exprs.top)
           push exprs { commandId, command, argIndex: 0 }

  number : check currentParam(exprs.top) == 'n'
           cells[cellIndex++] = data(number)
           exprs.top.argIndex++

  string : check currentParam(exprs.top) == 's'
           var entry = find token in strings
           if entry is none:
             if strings is full: error "Too many strings"
             entry = push strings { string: token, poolOffset: poolCells }
             poolCells += stringCellCount(token.length)
           cells[cellIndex++] = data(entry.poolOffset)
           exprs.top.argIndex++

  ')'    : var expr = pop exprs
           check expr.argIndex is a valid count for expr.command.params
           cells[cellIndex++] = call(expr.commandId, expr.argIndex)
           if exprs not empty: exprs.top.argIndex++

  END    : error "Unclosed '('"
while exprs not empty

cells[cellIndex++] = call(returnId, 0)
cells[base + 1] = cellIndex - base   poolOffset
for each entry in strings:
  cellIndex += writeString(cells[cellIndex], entry.string)
reverse units[firstChild ...]        so the first child is on top

skipToMatchingClose is a depth counter: read tokens, add one for every ( and subtract one for every ), and stop when the count returns to zero. Parentheses inside string literals are not a problem, because the tokeniser has already turned those into string tokens.

The frames for sub-units are pushed in source order, which leaves the last one on top. The reverse at the end puts the first one on top instead, so that sub-units are compiled, and laid out, in the order they appear in the source.

When the loop ends, the unit’s own cells are finished except for two things: its unitLength, and the placeholders for its sub-units. Neither can be filled in until the sub-units have been placed, which is the subject of the next section.

9Placing sub-units without recursion

A unit cannot be finished until its children are, and its children cannot be placed until it has written its own cells.

The recursive version is easy to describe: compile the unit, then for each sub-expression it skipped, compile a child unit at the current end of the buffer, patch the placeholder with childBase - base, and add the child’s length. Finally write unitLength. Each child places its own children the same way before returning, so the whole subtree ends up inside the parent’s span.

To do that without recursion, replace the call stack with an explicit stack of unit frames. A frame is a unit that has been found but not yet finished. It may not even have been compiled: listing 9 pushes a frame for every sub-expression it skips, and that frame only gets a base when it is compiled.

Listing 10. A unit frame
UnitFrame:
  base              cell where this unit starts, set when it is compiled
  exprStart         cursor of this unit's '('
  parentBase        base of the parent unit, or none for a root
  placeholder       cell in the parent to patch, or none for a root
  compiled          false until it has been compiled

The loop looks at the frame on top of the stack and does one of two things:

  1. Not compiled yet: set its base to the current end of the buffer and compile it with listing 9, which pushes a frame above it for each of its sub-units.
  2. Already compiled: every frame that was above it has been finished and popped, so all of its sub-units are in place. Write its unitLength as cellIndex - base, patch its placeholder in the parent with base - parentBase, and pop it.

This is correct because a frame is only ever compiled when it is on top, and a parent always sits below its children. When a child is compiled, everything it writes, and everything its own children write, lands before the next frame down is compiled. Each child therefore finishes completely before its next sibling starts, and the siblings land one after another inside the parent, after its pool, which is exactly the layout in figure 1. When the parent reaches the top again, cellIndex is past its last descendant, so cellIndex - base is its full length.

Why the expression stack stays separate

Listing 9 pushes frames while expressions are still open. If both lived on one stack, a frame would sit on top of the expression being read and exprs.top would no longer be it. The expression stack is also empty between units, so it never needs to share space with frames anyway.

10The whole compiler

Putting the pieces together, with an outer loop over the root expressions, gives the whole of compileScript. Listing 9 is written out in place. The continue inside the token loop moves on to the next token; the one after it goes back to the top of the unit loop.

Listing 11. compileScriptone function, no recursion
compileScript(script, privileged):
  var cells      = allocate(capacity)
  var cellIndex  = 0
  var rootCursor = 0
  var units      = stack of UnitFrame
  var exprs      = stack of Expression
  var strings    = list of UnitString

  loop:                                    one iteration per root
    var token = peekToken(script, rootCursor)
    if token is END: break
    if token is not '(': error "Expected '(' at top level"

    push units { exprStart: rootCursor, parentBase: none,
                 placeholder: none, compiled: false }

    while units not empty:
      var unit = units.top

      if not unit.compiled:
        unit.compiled = true
        unit.base = cellIndex
        var base = unit.base

        cellIndex = base + 2
        clear exprs
        clear strings
        var poolCells = 0
        var cursor = unit.exprStart
        var firstChild = units.length

        do:
          var open  = cursor
          var token = nextToken(script, &cursor)

          '('    : var name = nextToken(script, &cursor)
                   var command = lookup(name) or error "Unknown command"
                   if command.protected and not privileged: error "Command is protected"
                   if exprs not empty and currentParam(exprs.top) == 'x':
                     if units is full: error "Too many sub-expressions"
                     push units { exprStart: open, parentBase: base,
                                  placeholder: cellIndex, compiled: false }
                     cells[cellIndex++] = placeholder
                     skipToMatchingClose(script, &cursor)
                     exprs.top.argIndex++
                     continue
                   if exprs not empty:
                     check returnType(command) fits currentParam(exprs.top)
                   push exprs { commandId, command, argIndex: 0 }

          number : check currentParam(exprs.top) == 'n'
                   cells[cellIndex++] = data(number)
                   exprs.top.argIndex++

          string : check currentParam(exprs.top) == 's'
                   var entry = find token in strings
                   if entry is none:
                     if strings is full: error "Too many strings"
                     entry = push strings { string: token, poolOffset: poolCells }
                     poolCells += stringCellCount(token.length)
                   cells[cellIndex++] = data(entry.poolOffset)
                   exprs.top.argIndex++

          ')'    : var expr = pop exprs
                   check expr.argIndex is a valid count for expr.command.params
                   cells[cellIndex++] = call(expr.commandId, expr.argIndex)
                   if exprs not empty: exprs.top.argIndex++

          END    : error "Unclosed '('"
        while exprs not empty

        cells[cellIndex++] = call(returnId, 0)
        cells[base + 1] = cellIndex - base
        for each entry in strings:
          cellIndex += writeString(cells[cellIndex], entry.string)
        reverse units[firstChild ...]

        if unit.parentBase is none: rootCursor = cursor
        continue

      cells[unit.base] = cellIndex - unit.base
      if unit.placeholder is not none:
        cells[unit.placeholder] = data(unit.base - unit.parentBase)
      pop units

  cells[cellIndex] = 0                   end of the root list
  return cells

The line rootCursor = cursor only runs for a root, once it has been compiled. At that point cursor is just past the root’s closing ), which is where the next root begins. Sub-units never move the root cursor: their source text is inside the root’s and has already been passed.

Every error path does the same thing: log the message, rewind the arena to where it was before cells was allocated, and return nothing. Nothing outside the cell buffer has been touched, so there is nothing else to undo.

Part III · Running it

11What the VM needs

The VM has to know which unit it is in, because every offset is relative to that unit. So each frame of execution carries a base as well as a position:

  • Entering a unit at base means starting at base + 2, straight after the header.
  • A string argument $n is the string at base + cells[base + 1] + n: the unit’s base, plus its poolOffset, plus the string’s place in the pool.
  • A sub-expression argument @n is the unit at base + n. A command such as if runs it by pushing a new frame with that base, and the child’s return pops the frame and resumes the parent.
  • A return at root level moves on to the next root, at base + cells[base]. If the length there is 0, the script has finished.

Note that return is not the same as end. end stops the whole script, while return only leaves the current unit.

12Limits and trade-offs

  • Stack sizes. The expression stack only holds one unit’s open calls, so it is bounded by how deeply calls nest inside one unit, and the nesting depth limit is the right size for it. The unit stack has no such bound. It holds the chain of units from the root to the one being compiled, and also every sibling along that chain that has not been started yet. A single unit such as (do (if a b) (if c d) ...) pushes two frames for every if, however shallow it is. So give the unit stack its own limit, a few hundred frames being far more than any hand-written script needs, and check it before every push. That one check covers both deep nesting and wide units.
  • Strings per unit. The string list is cleared for every unit, so it only needs to hold the distinct strings of one unit. A few dozen is plenty, with an error if a unit goes over.
  • Repeated strings. Strings are only shared within a unit. A string used in five sub-units is stored five times. That is the price of each unit being self-contained.
  • One pass, plus skipping. Every unit’s source is tokenised once to compile it, and the source of a sub-expression is also skipped over once by each of its ancestors. Scripts are short and the tokeniser is cheap, so this rarely matters, and it saves keeping a buffer of tokens.
  • Offsets only point forwards. A unit can never refer to anything before its base or after its end. That is what makes copying safe, and it is also why a sub-expression cannot jump back to its parent: it can only return.
  • Size. Offsets are 31-bit data cells, and argument counts 16 bits, which is far more than any script needs.

Scripts: a cell format in which every piece of a compiled program can be copied out on its own, and a compiler that produces it in one pass per unit with a stack.
