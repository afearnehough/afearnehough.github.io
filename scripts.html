A script in the engine is a short program written as nested brackets, such as (if (near-player) (print "Hello")). Before it can run, it is compiled into a flat array of 32-bit numbers called cells, which a small virtual machine steps through one at a time.

This article describes a cell layout with one particular property: any piece of a compiled script can be lifted out and copied somewhere else without being changed. An entity can keep only the cells for its own behaviour, and everything else the script produced can be thrown away. Getting that property costs very little, but it has to be designed in from the start, because it rules out the obvious way of pointing from one cell to another.

Part I describes the format. Part II builds the compiler that produces it, first one pass at a time and then as a single function with no recursion. Part III covers what the virtual machine has to do to run it.

How to read the code in this article

The listings are pseudocode. They are close to C, and read top to bottom, but they leave out error handling and memory management so that the shape of the algorithm stays visible. push, pop and top act on small fixed-size stacks. A line that says error means: log the problem, give back the memory, and return nothing.

Part I · The format

1What we are building

Take two lines of script:

Listing 1. Two root expressions
(print "Hello World")
(print "Goodbye")

Each line that stands on its own is a root expression. The compiled output keeps them separate and in order: the strings one root needs, then its code, then the strings the next root needs, then its code.

Listing 2. The shape of the output
[strings][code]  [strings][code]
 root 1           root 2

Some commands take another expression as an argument, without running it straight away. if is the obvious one: (if (print "Hi") (print "Bye")) must decide which of its two branches runs. An argument like that is a sub-expression, and the compiler treats it exactly like a root: it gets its own strings and its own code, and it is placed after the code of the expression that owns it.

Listing 3. Sub-expressions get the same treatment
[if: strings][if: code]
  [Hi: strings][Hi: code]
  [Bye: strings][Bye: code]

Every block of the form [strings][code], whether it came from a root or a sub-expression, is called a unit. The rest of the article is about how units are laid out, how they refer to each other, and how to produce them.

2Cells

One 32-bit number, two possible meanings, told apart by the top bit.

A cell is a u32. The top bit says what kind of cell it is, and the other 31 bits hold its contents.

TypeTop bitRemaining bitsUsed for
Data031 bits of value Numbers, string offsets, sub-unit offsets, lengths, string characters
Call115 bits of command id, 16 bits of argument count Running a command

Code is written in postfix order: the arguments come first and the call comes last. (print "Hi") becomes a data cell that says where "Hi" is, followed by a call cell that says print, with one argument. When the VM reaches the call it already has the argument in hand, so nothing needs to look ahead.

A string is stored as one data cell holding its length, followed by its characters packed four to a cell. "Hi" takes two cells; "Hello World" takes four.

3Units

Everything a unit needs lives inside it, and it only ever points forwards into itself.

Every unit has the same layout:

Listing 4. One unit
[unitLength]      total cells in this unit, sub-units included
[codeOffset]      cells from the start of the unit to its first code cell
[string pool]     length-prefixed strings, then a 0 cell
[code]            postfix: arguments, then the call
[return]          a call cell meaning "leave this unit"
[sub-unit] ...    each one is a complete unit

The first cell of a unit is its base. Three rules make the whole scheme work:

  1. Every reference is relative to the base. A string argument is stored as “the string that starts 2 cells into this unit”, never as “the string at cell 9”. A sub-expression argument is stored as “the unit that starts 7 cells into this one”.
  2. Sub-units live inside their parent. They are placed after the parent’s return, and the parent’s unitLength counts them. A unit and everything it can reach form one contiguous run of cells.
  3. The header holds lengths, not jumps. The VM does not need a jump to get past the strings: it reads codeOffset and starts there. And anything that wants to copy a unit reads unitLength and knows how many cells to take.

A whole script is just its root units placed one after another, with a single 0 cell at the end. A unitLength of zero can never happen in a real unit, since the header alone is two cells, so it serves as the end marker.

Listing 5. A whole script
[root unit][root unit] ... [root unit][0]

4A worked example

Here is (if (print "Hi") (print "Bye")) compiled, cell by cell. The root unit holds if and has no strings of its own. Its two arguments are sub-units, so its code is two offsets and a call.

Walk through the Hi unit, which starts at cell 7. Its first cell says it is 8 cells long. Its second says the code starts 5 cells in, at cell 12, which skips the header, the string and the 0 that ends the pool. At cell 12 is @2, meaning the string 2 cells into this unit: cell 9, which holds the length 2, followed by the characters Hi. Then pr/1 prints it, and ret hands control back to whoever ran the unit.

The root unit’s length is 23 because it includes both sub-units. Its pool is empty, so it is a single 0 cell, and its code starts at cell 3.

5Copying a unit

Suppose an entity only needs the Hi branch. Copying it is one call:

Listing 6. Extracting a unitno fix-ups
length = cells[base]
memcpy(newCells, cells + base, length * sizeof(u32))

In the new buffer the unit starts at cell 0 instead of cell 7, and nothing inside it needs to change. Its @2 still means “2 cells from my base”, and the base has moved along with it. If the unit had sub-units of its own, they would have been copied too, because they sit inside its length.

The same works for a whole root: copy unitLength cells and you have a self-contained program. Once every entity has copied the unit it needs, the original compiled script can be discarded.

Why not absolute indices?

With absolute indices, cell 12 would say “the string at cell 9”. Copy the unit to cell 0 and that is now wrong, so every reference would need to be found and rewritten. To find them you would need to know which data cells are references and which are plain numbers, which means decoding the code. Relative offsets avoid the question entirely.

Summary
  • A unit is a header, a string pool, code, a return, and its sub-units, in that order.
  • Every reference is an offset from the unit’s first cell.
  • A unit contains everything it can reach, so unitLength cells starting at its base can be copied anywhere.

Part II · The compiler

6Params and the expression stack

Both passes need to know, for every argument, what kind of argument the command expects in that position.

Each registered command has a params string. Its first character is what the command returns, and each character after that describes one argument.

CharacterMeaning
vVoid: returns nothing (return position only)
nA number
sA string
xA sub-expression, compiled as its own unit
+The previous argument kind, repeated any number of times

So if might be vxx and print might be vs. While reading tokens, the compiler keeps a stack of open expressions. Each entry records the command and how many arguments have been read so far:

Listing 7. An open expression
Expression:
  commandId
  command
  argIndex          how many arguments have been read so far

currentParam(e):
  the kind of argument e expects next
  return e.command.params[1 + e.argIndex], with '+' repeating the character before it

The one rule that drives everything else: when a ( appears and the expression on top of the stack expects an x, the new expression is not part of the current unit. It will become a unit of its own later, so for now the compiler skips over it to its matching ).

A ( in any other position, such as a command that returns a number being used as a number argument, is an ordinary nested call. It is compiled inline, in postfix order, as part of the current unit, and its strings go in the current unit’s pool.

7Pass 1: the string pool

A unit’s strings come before its code, but the compiler does not know which strings the code needs until it has read it. The simplest answer is to read the unit’s tokens twice. The tokeniser’s position in the source text, chIndex, is all it needs to start again, so a unit is identified by the chIndex of its opening (.

The first pass collects strings. It skips sub-expressions in x positions, because their strings belong in their own pools, and it skips command names, which are not string arguments.

Listing 8. Pass 1strings only
at = base + 2                        after the two header cells
clear exprs
chIndex = unit.exprStart

do:
  token = nextToken(script, &chIndex)

  '('    : name = nextToken(script, &chIndex)
           command = lookup(name) or error "Unknown command"
           if exprs not empty and currentParam(exprs.top) == 'x':
             skipToMatchingClose(script, &chIndex)
             exprs.top.argIndex++
             continue
           push exprs { command, argIndex: 0 }

  string : if currentParam(exprs.top) == 's'
             and not searchString(cells[base + 2 ...], token):
             at += writeString(cells[at], token)
           exprs.top.argIndex++

  number : exprs.top.argIndex++

  ')'    : pop exprs
           if exprs not empty: exprs.top.argIndex++

  END    : error "Unclosed '('"
while exprs not empty

cells[at++] = 0                      end of the pool
cells[base + 1] = at - base          codeOffset

searchString walks the pool from its start until it reaches the 0 cell, and returns the offset of a matching string if there is one. That stops the same string being stored twice in one unit. Strings are not shared between units: a copied unit has to carry its own, so sharing would break section 5.

skipToMatchingClose is a depth counter: read tokens, add one for every ( and subtract one for every ), and stop when the count returns to zero. Parentheses inside string literals are not a problem, because the tokeniser has already turned those into string tokens.

8Pass 2: the code

The second pass reads the same tokens again and writes code cells after the pool. It is the same loop with three differences:

  • It checks each argument against the param it fills, and each command against privileged if the command is protected.
  • At every ) it writes the call cell. Because the arguments were written first, the output is postfix without any extra work.
  • When it meets a sub-expression in an x position, it writes a placeholder cell and pushes a frame for a new unit that has not been compiled yet. The frame records where the placeholder is and where the sub-expression starts in the source. Frames are explained in the next section.
Listing 9. Pass 2code cells
clear exprs
chIndex = unit.exprStart
firstChild = units.length

do:
  open  = chIndex
  token = nextToken(script, &chIndex)

  '('    : name = nextToken(script, &chIndex)
           command = lookup(name)
           if command.protected and not privileged: error "Command is protected"
           if exprs not empty and currentParam(exprs.top) == 'x':
             if units is full: error "Too many sub-expressions"
             push units { exprStart: open, parentBase: base,
                          placeholder: at, compiled: false }
             cells[at++] = placeholder
             skipToMatchingClose(script, &chIndex)
             exprs.top.argIndex++
             continue
           if exprs not empty:
             check returnType(command) fits currentParam(exprs.top)
           push exprs { commandId, command, argIndex: 0 }

  number : check currentParam(exprs.top) == 'n'
           cells[at++] = data(number)
           exprs.top.argIndex++

  string : check currentParam(exprs.top) == 's'
           cells[at++] = data(2 + searchString(cells[base + 2 ...], token))
           exprs.top.argIndex++

  ')'    : expr = pop exprs
           check expr.argIndex is a valid count for expr.command.params
           cells[at++] = call(expr.commandId, expr.argIndex)
           if exprs not empty: exprs.top.argIndex++
while exprs not empty

cells[at++] = call(returnId, 0)
reverse units[firstChild ...]        so the first child is on top

The 2 + on the string offset is there because searchString returns an offset from the start of the pool, and the pool starts two cells after the base.

The frames for sub-units are pushed in source order, which leaves the last one on top. The reverse at the end puts the first one on top instead, so that sub-units are compiled, and laid out, in the order they appear in the source.

When pass 2 ends, the unit’s own cells are finished except for two things: its unitLength, and the placeholders for its sub-units. Neither can be filled in until the sub-units have been placed, which is the subject of the next section.

9Placing sub-units without recursion

A unit cannot be finished until its children are, and its children cannot be placed until it has written its own code.

The recursive version is easy to describe: compile the unit, then for each sub-expression it skipped, compile a child unit at the current end of the buffer, patch the placeholder with childBase - base, and add the child’s length. Finally write unitLength. Each child places its own children the same way before returning, so the whole subtree ends up inside the parent’s span.

To do that without recursion, replace the call stack with an explicit stack of unit frames. A frame is a unit that has been found but not yet finished. It may not even have been compiled: pass 2 pushes a frame for every sub-expression it skips, and that frame only gets a base when it is compiled.

Listing 10. A unit frame
UnitFrame:
  base              cell where this unit starts, set when it is compiled
  exprStart         chIndex of this unit's '('
  parentBase        base of the parent unit, or none for a root
  placeholder       cell in the parent to patch, or none for a root
  compiled          false until both passes have run

The loop looks at the frame on top of the stack and does one of two things:

  1. Not compiled yet: set its base to the current end of the buffer and run both passes. Pass 2 pushes a frame above it for each of its sub-units.
  2. Already compiled: every frame that was above it has been finished and popped, so all of its sub-units are in place. Write its unitLength as at - base, patch its placeholder in the parent with base - parentBase, and pop it.

This is correct because a frame is only ever compiled when it is on top, and a parent always sits below its children. When a child is compiled, everything it writes, and everything its own children write, lands before the next frame down is compiled. Each child therefore finishes completely before its next sibling starts, and the siblings land one after another inside the parent, which is exactly the layout in figure 1. When the parent reaches the top again, at is past its last descendant, so at - base is its full length.

Why the expression stack stays separate

Pass 2 pushes frames while expressions are still open. If both lived on one stack, a frame would sit on top of the expression being read and exprs.top would no longer be it. The expression stack is also empty between units, so it never needs to share space with frames anyway.

10The whole compiler

Putting the pieces together, with an outer loop over the root expressions, gives the whole of compileScript. Pass 1 and pass 2 are listings 8 and 9, written out in place. The continue inside each pass moves on to the next token; the one after pass 2 goes back to the top of the unit loop.

Listing 11. compileScriptone function, no recursion
compileScript(script, privileged):
  cells  = allocate(capacity)
  at     = 0
  cursor = 0
  units  = stack of UnitFrame
  exprs  = stack of Expression

  loop:                                    one iteration per root
    token = peekToken(script, cursor)
    if token is END: break
    if token is not '(': error "Expected '(' at top level"

    push units { exprStart: cursor, parentBase: none,
                 placeholder: none, compiled: false }

    while units not empty:
      unit = units.top

      if not unit.compiled:
        unit.compiled = true
        unit.base = at
        base = unit.base

        pass 1: the string pool
        at = base + 2
        clear exprs
        chIndex = unit.exprStart

        do:
          token = nextToken(script, &chIndex)

          '('    : name = nextToken(script, &chIndex)
                   command = lookup(name) or error "Unknown command"
                   if exprs not empty and currentParam(exprs.top) == 'x':
                     skipToMatchingClose(script, &chIndex)
                     exprs.top.argIndex++
                     continue
                   push exprs { command, argIndex: 0 }

          string : if currentParam(exprs.top) == 's'
                     and not searchString(cells[base + 2 ...], token):
                     at += writeString(cells[at], token)
                   exprs.top.argIndex++

          number : exprs.top.argIndex++

          ')'    : pop exprs
                   if exprs not empty: exprs.top.argIndex++

          END    : error "Unclosed '('"
        while exprs not empty

        cells[at++] = 0
        cells[base + 1] = at - base

        pass 2: the code
        clear exprs
        chIndex = unit.exprStart
        firstChild = units.length

        do:
          open  = chIndex
          token = nextToken(script, &chIndex)

          '('    : name = nextToken(script, &chIndex)
                   command = lookup(name)
                   if command.protected and not privileged: error "Command is protected"
                   if exprs not empty and currentParam(exprs.top) == 'x':
                     if units is full: error "Too many sub-expressions"
                     push units { exprStart: open, parentBase: base,
                                  placeholder: at, compiled: false }
                     cells[at++] = placeholder
                     skipToMatchingClose(script, &chIndex)
                     exprs.top.argIndex++
                     continue
                   if exprs not empty:
                     check returnType(command) fits currentParam(exprs.top)
                   push exprs { commandId, command, argIndex: 0 }

          number : check currentParam(exprs.top) == 'n'
                   cells[at++] = data(number)
                   exprs.top.argIndex++

          string : check currentParam(exprs.top) == 's'
                   cells[at++] = data(2 + searchString(cells[base + 2 ...], token))
                   exprs.top.argIndex++

          ')'    : expr = pop exprs
                   check expr.argIndex is a valid count for expr.command.params
                   cells[at++] = call(expr.commandId, expr.argIndex)
                   if exprs not empty: exprs.top.argIndex++
        while exprs not empty

        cells[at++] = call(returnId, 0)
        reverse units[firstChild ...]

        if unit.parentBase is none: cursor = chIndex
        continue

      cells[unit.base] = at - unit.base
      if unit.placeholder is not none:
        cells[unit.placeholder] = data(unit.base - unit.parentBase)
      pop units

  cells[at] = 0                            end of the root list
  return cells

The line cursor = chIndex only runs for a root, after its pass 2. At that point chIndex is just past the root’s closing ), which is where the next root begins. Sub-units never move the cursor: their source text is inside the root’s and has already been passed.

Every error path does the same thing: log the message, rewind the arena to where it was before cells was allocated, and return nothing. Nothing outside the cell buffer has been touched, so there is nothing else to undo.

Hi is compiled at cell 7 and pushes nothing, so on the next turn of the loop it is finished: it writes its length 8, patches cell 3 with 7 - 0, and pops. Bye does the same at cell 15 and patches cell 4. The root is on top again, writes its length 23, and pops. Compare the result with figure 1.

Part III · Running it

11What the VM needs

The VM has to know which unit it is in, because every offset is relative to that unit. So each frame of execution carries a base as well as a position:

  • Entering a unit at base means starting at base + cells[base + 1].
  • A string argument @n is the string at base + n.
  • A sub-expression argument @n is the unit at base + n. A command such as if runs it by pushing a new frame with that base, and the child’s return pops the frame and resumes the parent.
  • A return at root level moves on to the next root, at base + cells[base]. If the length there is 0, the script has finished.

Note that return is not the same as end. end stops the whole script, while return only leaves the current unit.

12Limits and trade-offs

  • Stack sizes. The expression stack only holds one unit’s open calls, so it is bounded by how deeply calls nest inside one unit, and the nesting depth limit is the right size for it. The unit stack has no such bound. It holds the chain of units from the root to the one being compiled, and also every sibling along that chain that has not been started yet. A single unit such as (do (if a b) (if c d) ...) pushes two frames for every if, however shallow it is. So give the unit stack its own limit, a few hundred frames being far more than any hand-written script needs, and check it in pass 2 before every push. That one check covers both deep nesting and wide units.
  • Repeated strings. Strings are only shared within a unit. A string used in five sub-units is stored five times. That is the price of each unit being self-contained.
  • Two passes. Every unit’s source is tokenised twice, and the source of a sub-expression is also skipped over once by each of its ancestors. Scripts are short and the tokeniser is cheap, so this rarely matters, and it saves keeping a buffer of tokens.
  • Offsets only point forwards. A unit can never refer to anything before its base or after its end. That is what makes copying safe, and it is also why a sub-expression cannot jump back to its parent: it can only return.
  • Size. Offsets are 31-bit data cells, and argument counts 16 bits, which is far more than any script needs.

Scripts: a cell format in which every piece of a compiled program can be copied out on its own, and a compiler that produces it with two passes and a stack.
